    # 微信小程序

    # 1.小程序的技术架构与文件类型

    核心文件：

    WXML：相当于网页的HTML，用于描述页面结构。

    WXSS：相当于CSS，用于描述样式，支持 rpx 自适应单位。

    JS：逻辑交互文件。

    JSON：配置文件（如 app.json 全局配置，project.config.json 工具配置）。

    双线程模型：

    渲染层：使用 WebView 进行页面渲染。

    逻辑层：使用 JSCore 运行 JS 代码。

    关键点：逻辑层和渲染层是分离的，通过 Native 的 JSBridge 进行通信。这种设计避免了单线程阻塞，但也意味着无法直接操作 DOM。

    # 2.生命周期

    应用生命周期（App 对象）：

    onLaunch：首次初始化（全局只触发一次）。

    onShow：启动或从后台切回前台。

    onHide：从前台切到后台。

    页面生命周期（Page 对象）：

    onLoad：页面加载，可获取路由参数（只触发一次）。

    onShow：页面显示/切入前台。

    onReady：页面初次渲染完成（只触发一次）。

    onHide：页面隐藏/切入后台。

    onUnload：页面卸载。

    执行顺序：App onLaunch -> App onShow -> Page onLoad -> Page onShow -> Page onReady

    # 3.WXML 与 HTML、WXSS 与 CSS 的异同

    WXML vs HTML：

    标签名不同（如 view 代替 div，button 封装更严）。

    拥有 wx:if、wx:for 等逻辑语法。

    没有 window 和 document 对象，无法操作 DOM。

    WXSS vs CSS：

    rpx (responsive pixel)：独有的响应式单位，会根据屏幕宽度自适应，是适配不同手机的关键。

    样式隔离：默认支持组件样式隔离。

    不支持部分复杂选择器。

    # 4.数据绑定与 setData

    与 Vue/React 的区别：小程序不能直接使用 this.data.xxx = value 修改数据。

    核心机制：必须使用 this.setData({ ... }) 触发界面更新。

    陷阱：setData 是同步的还是异步的？

    逻辑层的 setData 操作是异步的（为了通过 JSBridge 传输数据），但 setData 后的 this.data 更新是同步的（立即生效）。

    性能优化：避免频繁调用 setData，合并数据更新；避免在 setData 中传输大量数据，否则会导致页面卡顿

    # 5.路由与跳转

    wx.navigateTo：保留当前页面，跳转到新页面（使用 wx.navigateBack 返回）。页面栈最多 10 层。

    wx.redirectTo：关闭当前页面，跳转新页面（无法返回）。

    wx.reLaunch：关闭所有页面，打开新页面。

    wx.switchTab：跳转到 tabBar 页面，并关闭其他非 tabBar 页面。

    # 6.组件通信

    父子组件：properties（父传子）、triggerEvent（子传父）。

    跨页面通信：

    全局数据：getApp().globalData。

    事件总线：通常需要借助第三方库或自行实现。

    数据缓存：wx.setStorageSync。

    # 7.性能优化

    分包加载：主包不超过 2M，总包不超过 20M。通过 subpackages 配置，按需加载，减少首屏时间

    预加载：利用 preloadRule 配置，在网络空闲时预加载分包。

    渲染方面：减少 setData 的数据量和使用频次；避免在 onPageScroll 等高频事件中频繁调用 setData

    图片处理：使用 WebP 格式（iOS 14+ 支持），上传 CDN，懒加载。

    代码方面：避免过深的 WXML 结构，合理使用 wx:if 和 hidden（hidden 适合频繁切换，wx:if 适合初始渲染条件分支较少的情况）

    # 8.对微信小程序"分包加载"的理解

    分包加载是为了解决小程序启动时下载慢的问题。将小程序代码拆分成主包和分包。启动时只下载主包（首页），当用户跳转到分包页面时，再异步下载分包。这能显著降低首屏加载时间。限制是主包不超过 2M，总包不超过 20M。

    # 9.小程序的登录流程

    核心是 wx.login 获取 code，然后后端拿着 code + appid + secret 请求微信接口换取 openid 和 session_key。后端自定义生成 3rd_session 返回给前端，前端存入 storage 中，后续请求带上这个自定义 session 来识别用户身份

    # 10.小程序分包及预加载

    目录结构建议：

    
├── app.js

├── app.json

├── packageA/          # 分包A

│   └── pages/

│       └── shop/

├── packageB/          # 分包B

│   └── pages/

│       └── user/

└── pages/             # 主包页面

    └── index/

    在 app.json 中配置 subpackages：

    
{

    "pages": [

        "pages/index/index"    // 主包页面（首页必须放在主包）

    ],

    "subpackages": [

        {

        "root": "packageA",   // 分包根目录

        "name": "shop",       // 分包别名（可选）

        "pages": [            // 分包下的页面路径（相对于root）

            "pages/shop/shop",

            "pages/detail/detail"

        ]

        },

        {

        "root": "packageB",

        "name": "user",

        "pages": [

            "pages/user/user"

        ]

        }

    ],

    "preloadRule": {          // 预加载配置（见下文）

        "pages/index/index": {

        "network": "all",

        "packages": ["shop"]

        }

    }

}

    为什么要预加载？

    如果不预加载，用户点击分包页面时才下载分包，会有明显的网络延迟和"白屏等待"。预加载可以在主包空闲时提前下载分包。

    1. 配置式预加载（推荐）

    在 app.json 的 preloadRule 中配置，当进入某个页面时触发预加载：

    
{

    "preloadRule": {

        "pages/index/index": {           // 触发预加载的页面路径

        "network": "all",              // 网络条件：all（不限）/ wifi（仅WiFi）

        "packages": ["shop", "user"]   // 要预加载的分包名（name字段）

        },

        "pages/category/category": {     // 也可以在其他页面触发

        "network": "wifi",

        "packages": ["shop"]

        }

    }

}
    1. 代码手动预加载

    在页面的 onLoad 或 onReady 中手动调用：

    
// pages/index/index.js

onLoad() {

    // 预加载 shop 分包

    wx.loadSubpackage({

        name: 'shop',      // 分包别名（name字段）

        success(res) {

        console.log('分包预加载成功', res)

        },

        fail(err) {

        console.error('预加载失败', err)

        }

    })

}

    独立分包（高级进阶）

    独立分包是一种特殊分包，可以不依赖主包独立运行。适合"不启动主程序也能用"的页面（如：活动页、分享页）。

    
{

    "subpackages": [

        {

        "root": "packageActivity",

        "pages": ["pages/activity/activity"],

        "independent": true   // 关键配置：标记为独立分包

        }

    ]

}

    特点：

    独立分包可以不下载主包直接打开（前提是入口不在主包）

    不能使用主包中的资源（代码、图片、全局变量等）

    适合做活动页面、落地页，提升分享打开速度

    # 11.微信小程序支付流程

    第1步：用户登录，获取 openid

    用户进入小程序后，调用 wx.login 获取临时 code，传给后端换取 openid。

    
// 小程序端

wx.login({

    success(res) {

        if (res.code) {

        // 将 code 发送给后端

        wx.request({

            url: 'https://your-domain/api/getOpenid',

            data: { code: res.code },

            success: (result) => {

            const openid = result.data.openid;

            // 保存 openid 供后续支付使用

            }

        });

        }

    }

});

    重点：openid 是用户在当前小程序下的唯一标识，同一个用户在不同小程序的 openid 不同。

    第2步：用户下单，后端调用统一下单接口

    用户点击"立即支付"后，小程序将订单信息（商品ID、金额等）发送给后端。后端调用微信支付统一下单API，获取 prepay_id。

    第3步：后端二次签名，返回调起支付参数

    后端拿到 prepay_id 后，按照微信支付要求的签名规则进行二次签名，生成调起支付所需的完整参数，返回给小程序端。

    返回给前端的参数结构：

    
{

    "timeStamp": "1737000000",     // 时间戳

    "nonceStr": "abc123xyz",       // 随机字符串

    "package": "prepay_id=wx123...",// 预支付会话标识

    "signType": "RSA",             // 签名类型

    "paySign": "xxxxx"             // 签名

}

    第4步：小程序调起支付

    小程序收到后端返回的参数后，调用 wx.requestPayment 拉起微信支付收银台。

    
// 小程序端

wx.requestPayment({

    timeStamp: data.timeStamp,

    nonceStr: data.nonceStr,

    package: data.package,

    signType: data.signType,

    paySign: data.paySign,

    success: (res) => {

        // ⚠️ 注意：这里的success不代表支付成功！

        // 仅代表用户成功调起了支付，或支付完成点击了完成按钮

        // 需要主动向后端查单确认真实支付状态

        checkOrderStatus();

    },

    fail: (err) => {

        // 用户取消支付或支付失败

        console.log('支付失败', err);

    }

});

    总结：小程序支付流程 = 前端获取openid → 后端下单获prepay_id → 二次签名返回参数 → 前端调起支付 → 后端异步通知 + 前端主动查单双重确认，最终以查单结果为准更新订单状态。
